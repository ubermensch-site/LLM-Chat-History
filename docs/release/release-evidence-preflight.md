# v0.1 Release QA Evidence Preflight

This preflight is the final local evidence check for TASK-054 after authenticated ChatGPT QA has been completed against the pinned release candidate.

It does **not** replace the live scenarios in `docs/qa/live-chatgpt-validation.md`. It verifies that the evidence set is complete, privacy-safe, structurally consistent, tied to the expected candidate metadata, and that every scenario has been explicitly marked PASS by the human tester.

## 1. Prepare a local evidence directory

Copy the checked-in template:

```bash
mkdir -p qa-evidence/v0.1
cp docs/release/qa-session.example.json qa-evidence/v0.1/qa-session.json
```

`qa-evidence/` is ignored by Git by default.

Use the exact candidate encoded in the template unless issue #3 has explicitly pinned a newer build.

## 2. Run the authenticated scenarios

Follow `docs/qa/live-chatgpt-validation.md`.

At each requested checkpoint use the recorder **QA report** button and save the downloaded JSON into `qa-evidence/v0.1/` using the filenames already listed in `qa-session.json`.

The QA reports are content-safe by schema: they contain structural selector counts, route-shape booleans, adapter/recorder/storage state, and count-only archive status. They do not contain prompt/answer text, raw URLs, conversation titles, provider conversation IDs, tags, projects/folders, or checkpoint notes.

## 3. Record the human outcome

For each scenario in `qa-session.json`:

- change `status` from `BLOCKED` to `PASS` only after the full scenario acceptance criteria are satisfied;
- keep a scenario `BLOCKED` or set it to another non-PASS value if it is incomplete or failed;
- update `notes` with concise reproduction information if needed;
- fill in browser version, OS, tester, and ISO-8601 test timestamp.

The preflight intentionally refuses any scenario that is not exactly `PASS`.

## 4. Run the preflight

```bash
npm run release:preflight -- --evidence qa-evidence/v0.1
```

A successful run prints:

```text
Release QA preflight PASS: 10 scenarios, <N> report(s)
```

and creates:

```text
qa-evidence/v0.1/release-qa-preflight.md
```

The Markdown summary is safe to paste into issue #3 / TASK-054 because it contains candidate metadata, environment information, scenario statuses, report counts, and the explicit limitation that preflight does not replay provider interactions.

## 5. What the preflight rejects

The command fails if any of the following is true:

- session/report schema is missing or has extra fields;
- a QA report claims privacy-bearing fields are present;
- a report was generated by a different extension version;
- structural evidence is contradictory (for example rendered turns with no semantic turn selectors);
- a conversation route has no canonical archive record;
- recorder and persisted archive states conflict;
- storage health reports an error;
- evidence paths are unsafe;
- candidate SHA/digests/CI metadata are malformed;
- any of scenarios 1–10 is missing, duplicated, or not explicitly `PASS`;
- any referenced QA report file is missing or malformed.

## Release boundary

A successful preflight is necessary but not sufficient for the final v0.1 release. The release can be approved only when:

1. issue #3 contains authenticated live evidence for all scenarios;
2. TASK-054 records the approved candidate SHA/artifact/checksums/environment;
3. the full CI/package/security gate passes for the final approved commit;
4. the release tag/package is created from that approved commit only.
