## 1. Prepare a local evidence directory

```bash
mkdir -p qa-evidence/v0.1
cp docs/release/qa-session.example.json qa-evidence/v0.1/qa-session.json
```

`qa-evidence/` is ignored by Git.

## 2. Run the authenticated scenarios

Follow `docs/qa/live-chatgpt-validation.md` using the exact pinned build.

At requested checkpoints use the recorder **QA report** action and save the downloaded JSON into `qa-evidence/v0.1/` using the filenames listed in `qa-session.json`.

The current QA report schema contains only structural/count/state evidence. Archive evidence includes:

- conversation found;
- message count;
- event count;
- visible activity count;
- persisted recorder state.

The report does **not** contain prompt text, assistant answer text, visible-activity text, raw URLs, conversation titles, provider conversation IDs, tags/projects/folders, or checkpoint notes.

## 3. Record the human outcome

For each scenario:

- change `status` from `BLOCKED` to `PASS` only after all scenario criteria are satisfied;
- leave it non-PASS if incomplete or failed;
- record concise notes where manual visual/behavior evidence matters;
- fill in browser version, OS, tester and ISO-8601 test time.

The preflight intentionally refuses any scenario that is not exactly `PASS`.

## 4. Run the preflight

```bash
npm run release:preflight -- --evidence qa-evidence/v0.1
```

A successful run creates:

```text
qa-evidence/v0.1/release-qa-preflight.md
qa-evidence/v0.1/release-approval.json
```

The Markdown summary is GitHub-safe. It contains candidate/environment/scenario metadata and count-only evidence summaries. The visible-activity number is only a sum across QA snapshots and may double-count the same activity across before/after reports; it is evidence that activity exists, not a unique-activity metric.

The machine-readable approval record contains only:

- candidate commit/version/artifact metadata and SHA-256 digests;
- CI run ID;
- browser/browser version/OS;
- test timestamp/tester;
- scenario count;
- validated report count;
- `allScenariosPass: true`.

It does not copy chat text, activity text, DOM details, titles or provider IDs.

## 5. What the preflight rejects

The command fails before approval output is written if any of the following is true:

- session/report schema is missing or has extra fields;
- a QA report contains an unexpected field that could carry private content;
- a report was generated by a different extension version;
- current reports omit the mandatory count-only `visibleActivityCount` field;
- structural evidence is contradictory;
- a conversation route has no canonical archive record;
- visible activity is reported without a canonical conversation/message;
- recorder and persisted states conflict;
- storage health reports an error;
- evidence paths are unsafe;
- candidate SHA/digests/CI metadata are malformed;
- any scenario 1–10 is missing, duplicated or not explicitly PASS;
- any referenced QA report is missing or malformed.

## Release boundary

A successful preflight is necessary but not sufficient. v0.1 can be finalized only when:

1. issue #3 contains authenticated evidence for scenarios 1–10;
2. changed behavior from the visible-activity/model/UX functional pass has been exercised live;
3. TASK-054 records the approved candidate/artifact/checksums/environment;
4. the full CI/build/security/package gate passes for the final release commit;
5. the release approval record matches the approved browser-tested candidate;
6. no runtime code change occurs after the last required live retest without another targeted retest;
7. issue #3 and #37 are closed only after all required evidence passes.
